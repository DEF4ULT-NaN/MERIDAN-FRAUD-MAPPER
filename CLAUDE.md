# Fraud Network Mapper — Project Brief

## 1. Vision

A Palantir-style investigative tool that turns raw account/transaction/social
data into a **visual, explainable fraud network map**. Instead of manually
digging through spreadsheets, a user uploads their data and instantly sees:

- Which accounts are secretly connected (shared IPs, devices, phones, banks)
- Which clusters look like coordinated fraud rings or bot networks
- A plain-English explanation of *why* each cluster is suspicious
- A risk score per account/cluster, generated by a Graph Neural Network (GNN)
  that learns suspicious patterns rather than relying on hardcoded rules

**One-line pitch:** "Upload your network activity, and we'll show you the
invisible web connecting fraudsters — and explain why we flagged them."

**Track:** Security, Identity & Trust
**Why this wins:** Technically deep (GNN + graph theory) but the demo is
instantly understandable to non-technical judges — a graph lighting up red
clusters is a strong visual "wow" moment.

---

## 2. Tech Stack

| Layer | Choice | Purpose |
|---|---|---|
| Frontend | React | Upload UI, dashboard, interactive graph |
| Graph visualization | `react-force-graph` or D3.js | Dynamic node/edge rendering, color-coded risk |
| Backend | Python + FastAPI | File upload handling, graph construction, GNN inference API |
| Graph construction | `networkx` | Build nodes/edges from tabular data |
| ML model | PyTorch Geometric (PyG) — GraphSAGE or GCN | Node-level fraud-risk classification |
| Synthetic data | Python + `faker` | Generate realistic fake accounts/transactions with planted fraud rings for training + demo |
| Clustering (optional/backup) | `networkx` Louvain community detection | Fallback if GNN scoring is incomplete |
| Export | `reportlab` or `weasyprint` | Generate a PDF "Fraud Report" |
| Model hosting | Pre-trained weights loaded at runtime | Never train live during the demo — too risky |

**Fallback rule:** If the GNN isn't reliably working by the demo, fall back to
the rule-based risk scorer (shared-attribute counting). The pitch can still
say "GNN-based" as long as a trained model is shown working on at least a
subset of the demo data.

---

## 3. Core User Flow

1. **Upload** — user drops in a CSV/JSON of account/transaction/login data,
   or selects a built-in sample dataset (critical for a reliable demo)
2. **Auto-detect columns** — tool guesses which columns are IDs, IPs,
   timestamps, amounts, etc.
3. **Processing screen** — animated steps: "Building graph → Running GNN →
   Scoring risk" (masks backend processing time, sells the AI narrative)
4. **Interactive graph output** — nodes = accounts, edges = shared
   attributes, color = risk score, clusters = suspicious rings
5. **Click-to-explain panel** — clicking a node/cluster shows a plain-English
   reason (e.g. "This cluster of 6 accounts shares 3 devices and transacted
   within a 2-minute window — 92% risk score")
6. **Export/report** — "Generate Fraud Report" button produces a clean PDF
   summary readable by a non-technical exec

## 4. Step-Wise Goals (resume from any step if interrupted)

### Phase A — Data Foundation
- [ ] **A1.** Write synthetic data generator (Python + `faker`): normal users
      + planted fraud rings sharing IP/device/phone/bank account
- [ ] **A2.** Export generator output as CSV/JSON sample datasets (for both
      training and demo use)
- [ ] **A3.** Label the synthetic data with ground-truth fraud/not-fraud tags
      (needed for GNN training)

### Phase B — Graph Construction
- [ ] **B1.** Write script to convert tabular data → graph structure
      (`networkx`): nodes = accounts, edges = shared attributes with a
      "reason" label
- [ ] **B2.** Add node features: transaction frequency, account age, degree,
      amount patterns
- [ ] **B3.** Add basic rule-based risk scorer (fallback path) — more shared
      connections = higher score

### Phase C — GNN Model
- [ ] **C1.** Set up PyTorch Geometric environment
- [ ] **C2.** Build GraphSAGE/GCN model architecture for node classification
- [ ] **C3.** Train model on synthetic labeled data
- [ ] **C4.** Validate model — check it correctly flags planted fraud rings
- [ ] **C5.** Save trained model weights for runtime inference (no live
      training during demo)

### Phase D — Backend API
- [ ] **D1.** Set up FastAPI project structure
- [ ] **D2.** Build `/upload` endpoint — accepts CSV/JSON, auto-detects
      column types
- [ ] **D3.** Build `/build-graph` endpoint — runs Phase B logic on uploaded
      data
- [ ] **D4.** Build `/score` endpoint — runs GNN inference (Phase C model) on
      the graph, returns risk scores
- [ ] **D5.** Build `/explain` endpoint — returns plain-English reason for a
      given node/cluster's score
- [ ] **D6.** Build `/report` endpoint — generates PDF summary

### Phase E — Frontend
- [ ] **E1.** Build upload screen (drag-drop + sample dataset option)
- [ ] **E2.** Build column auto-detect confirmation UI
- [ ] **E3.** Build animated "processing" screen
- [ ] **E4.** Build interactive graph view (`react-force-graph`/D3) with
      color-coded risk
- [ ] **E5.** Build click-to-explain side panel
- [ ] **E6.** Build summary dashboard (e.g. "3 fraud rings detected, 14
      linked accounts")
- [ ] **E7.** Wire up "Generate Report" button to backend `/report` endpoint

### Phase F — Integration & Demo Polish
- [ ] **F1.** Connect frontend to backend end-to-end, test full flow with
      sample dataset
- [ ] **F2.** Stress-test with messy/incomplete data — make sure it degrades
      gracefully (falls back to rule-based scorer if needed)
- [ ] **F3.** Polish visuals — consistent color scheme, smooth graph
      animations, loading states
- [ ] **F4.** Prepare demo script: problem → upload → processing → graph
      reveal → click explain → report export
- [ ] **F5.** Prepare backup: pre-recorded demo video / cached results in
      case of live-demo failure

## 6. Key Reminders
- Never rely on real APIs or live-fetched data — synthetic data keeps the
  demo reliable and repeatable
- Never train the GNN live during the demo — always load pre-trained weights
- Always have the rule-based scorer as a fallback path
- The "explain panel" is the biggest UX differentiator — don't cut it if
  time runs short
